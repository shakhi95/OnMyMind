# ON MY MIND LIST

## Complete Product, UX, Architecture & Engineering Specification

You are the primary coding agent responsible for designing and implementing this application.

Do not treat this as a generic todo-list project.

The application is a **private personal thinking and mental-management system**. Its purpose is to help one person get things out of their head, think about them, understand them, make decisions, remember what they decided, take action when appropriate, and intentionally let things go.

The product should feel calm, intelligent, private, lightweight, and trustworthy.

Do not over-engineer it.

Build a polished V1 first, with a clean architecture that allows V2/V3 features to be added later.

---

# 1. PRODUCT NAME

**On My Mind List**

Possible short name in UI:

**On My Mind**

---

# 2. PRODUCT PHILOSOPHY

The core problem is not simply task management.

The user frequently has many things in their head:

- tasks
- worries
- questions
- decisions
- ideas
- things they need to remember
- unfinished projects
- things they have already worked on
- things they want to revisit later
- things they are unsure about
- thoughts that repeatedly come back

The application should reduce cognitive load by giving these thoughts a safe external place.

The fundamental philosophy:

> If something is occupying my mind, I should be able to put it somewhere trustworthy.

And:

> I should not have to decide what something is before I capture it.

And:

> Thinking about something is valuable even when it produces no task.

And:

> Dropping something is not failure.

And:

> If something comes back into my mind later, I should be able to continue the existing thread instead of creating a duplicate.

The application is therefore closer to:

**Private journal + thinking system + lightweight action management**

than to:

**Todoist / Trello / project management software**

---

# 3. PRIMARY USER WORKFLOW

The user's real workflow is approximately:

1. Open the app.
2. Start a daily journal.
3. Write topics that are currently occupying their mind.
4. Give those topics numbers.
5. Think/write about each topic.
6. During that thinking, the user may:

   - reach a decision
   - discover an action
   - create one or more tasks
   - realize nothing needs to be done
   - decide to revisit it later
   - decide to drop it
   - continue an existing topic from previous days
   - discover that it is an ongoing project/thread

7. The user wants to see what they have already done.
8. The user wants to remember why they made decisions.
9. The user wants to see what remains to be done.
10. The user wants unfinished mental topics to stop floating around in their head.

The application should support this workflow naturally.

---

# 4. IMPORTANT PRODUCT PRINCIPLE

Do NOT force the user to classify every thought immediately.

Capture should be extremely low friction.

The user should be able to write:

> "I keep thinking about my website"

without first selecting:

- project
- task
- idea
- worry
- reference
- priority
- deadline
- category

The system should allow the thought to remain a thought while the user thinks.

Classification happens naturally as the user processes it.

---

# 5. TWO PRIMARY ENTRY MODES

The application must support two fundamentally different ways to use it.

## MODE A — JOURNAL / THINKING

The user does not know exactly what something is.

Example:

> "I'm worried about whether I should move."

They open today's journal and write about it.

Flow:

```text
Journal
  ↓
Thought
  ↓
Thinking
  ↓
Decision / Action / Later / Dropped / Nothing
```

---

## MODE B — QUICK TASK

The user already knows exactly what needs to happen.

Example:

> "Buy toothpaste"

They should NOT have to create a journal entry first.

They can directly create:

```text
Task: Buy toothpaste
```

Therefore:

```text
ON MY MIND

        ┌───────────────┐
        │               │
        ▼               ▼
    JOURNAL          QUICK ADD
        │               │
        ▼               ▼
    THOUGHT           TASK
        │
        ▼
     THINKING
```

This is a core requirement.

# 6. CORE DOMAIN CONCEPTS

Keep the conceptual model small.

Do not create dozens of item types.

The main concepts are:

## 6.1 Journal

A daily container for the user's thinking.

Example:

```text
October 1, 2026

What's on my mind?

1. Personal website
2. Money
3. Moving
4. Learning guitar
```

---

## 6.2 Thought

A topic captured during a journal session.

A thought does NOT necessarily need to become a task.

A thought can:

- remain only in the journal
- become connected to an existing Thread
- become a new Thread
- produce a Task
- produce a Decision
- be postponed
- be dropped

---

## 6.3 Thread

A persistent topic that continues across time.

This is extremely important.

If the user thinks:

> "Personal website"

on October 1,

and again on October 4,

the application should NOT create two unrelated things.

It should allow the user to continue the same Thread.

Example:

```text
THREAD
Personal Website

Oct 1
Initial thought:
"I need to finally build my website."

Oct 4
Came back to this.
I think the main reason I'm avoiding it is...

Oct 7
Decision:
I will build a simple version first.

Actions:
✓ Buy domain
✓ Create repository
→ Build homepage
```

A Thread represents something that continues to occupy the user's mind or requires ongoing attention.

---

## 6.4 Task

A concrete action that can be done.

Tasks can exist:

### Standalone

```text
Buy toothpaste
```

or:

### Attached to a Thread

```text
Thread: Personal Website

✓ Buy domain
✓ Create repository
→ Build homepage
```

A task does NOT require a Thread.

---

## 6.5 Decision

A decision is NOT necessarily a separate top-level item type.

A decision is an outcome of thinking.

Example:

```text
Question:
Should I buy a new laptop?

Thinking:
My current one is slow but still usable.

Decision:
I'll keep it for another year.

Result:
No task.
```

Or:

```text
Decision:
I'll buy one this month.

Result:
Task → Research laptops
```

The system should preserve decisions as part of the Thread/Journal history.

---

## 6.6 Later

A deliberate postponement.

Meaning:

> "I don't want to deal with this now, but I don't want to lose it."

This is different from dropping it.

---

## 6.7 Dropped

A deliberate release.

Meaning:

> "I have consciously decided that this no longer deserves my attention."

Dropped is not failure.

The UI should never use shame-oriented language.

Avoid:

- failed
- overdue failure
- neglected
- abandoned

Prefer:

- dropped
- released
- no longer active

---

# 7. IMPORTANT DISTINCTION: THOUGHT VS THREAD

Use this conceptual distinction:

### Thought

A moment of thinking captured in a journal.

### Thread

A persistent topic that can be revisited across multiple days.

Example:

```text
October 1 Journal
    ↓
Thought: "Personal website"
    ↓
Becomes Thread: Personal Website

October 4 Journal
    ↓
Revisit Personal Website Thread

October 10 Journal
    ↓
Revisit Personal Website Thread
```

The user should be able to reuse/revisit an existing Thread from a new daily journal.

This is one of the most important features of the product.

---

# 8. REVISITING OLD THOUGHTS / THREADS

When starting today's journal, the user should be able to see existing active Threads.

Example:

```text
Today's Journal

What's on your mind?

[ Write something... ]

--------------------------------

Continue something from before

Personal Website
Last thought: Yesterday

Moving
Last thought: 3 days ago

Money
Last thought: 5 days ago
```

Clicking one should add/revisit that Thread in today's journal.

It must NOT duplicate the Thread.

The user is continuing the existing mental thread.

# 10. NUMBERED THOUGHTS

The user's natural process is to number topics.

Support this explicitly.

Example:

```text
1. Website
2. Money
3. Mom's birthday
4. Moving
```

The system can automatically number thoughts within a journal.

The number should be visually prominent but subtle.

Do not force the user to manually type `1.`.

If they add another thought, automatically assign the next number.

Allow reordering if practical.

# 11. THINKING VIEW

Clicking a Thought should open a focused thinking interface.

Example:

```text
01

Personal Website

What are you thinking about?

┌───────────────────────────────────────────┐
│                                           │
│ I've been thinking about this because...  │
│                                           │
│ The real problem is...                    │
│                                           │
│ I think I should...                       │
│                                           │
└───────────────────────────────────────────┘

What came out of this?

○ Nothing for now
○ I made a decision
○ I need to do something
○ Continue later
○ I'm done with this
```

Do not force a structured form before the user has written.

The writing area should be the primary UI.

---

# 12. THINKING HISTORY

A Thread must preserve its history.

For example:

```text
Personal Website

THINKING HISTORY

Oct 1
I think I want a personal website because...

Oct 4
I keep coming back to this. The real issue is...

Oct 7
I decided to build a simple version first.

Oct 9
Bought the domain and started the homepage.
```

This history is important because the user explicitly wants to see what they have already done and feel progress.

---

# 13. PROGRESS / ACCOMPLISHMENT VIEW

For ongoing Threads, show completed work.

Example:

```text
Personal Website

Progress

✓ Bought domain
✓ Created repository
✓ Designed homepage
✓ Added about page

Current focus

→ Build projects section
```

The completed history should remain visible.

Do NOT hide completed tasks immediately.

The application is partially intended to help the user recognize progress.

---

# 14. FOCUS MODE

Focus Mode should be simple.

It should not become another dashboard.

For an active Thread:

```text
PERSONAL WEBSITE

You've already done:

✓ Domain
✓ Repository
✓ Homepage

Current focus:

→ Build projects section

[ Open Thread ]
```

If the Thread contains many tasks, Focus Mode should emphasize the next relevant unfinished action.

Do not show unnecessary metadata.

The goal is:

> "What should I focus on now?"

# 15. TASK CREATION

Support direct task creation from anywhere.

Global action:

```text
+
```

Options:

```text
New Task
New Thought

```

Potentially:

```text

```

if no journal exists for today.

For quick tasks:

```text

[ Buy toothpaste                 ]

[ Add Task ]
```

Do not force:

- priority
- project
- category
- due date
- tags

---

# 16. TASK STATES

Keep task states simple:

```ts
type TaskStatus = "open" | "done" | "dropped";
```

Do not create:

- blocked
- in progress
- paused
- archived
- postponed

unless there is a real V2 requirement.

A task being unfinished does not need a complicated state.

---

# 17. THREAD STATES

Use:

```ts
type ThreadStatus = "active" | "later" | "resolved" | "dropped";
```

Meaning:

### active

Currently relevant.

### later

Intentionally postponed.

### resolved

The topic has been dealt with.

### dropped

The user intentionally released it.

Do not use `done` for Threads.

A Thread isn't necessarily something that gets "done."

---

# 18. WHAT HAPPENS WHEN A THREAD IS RESOLVED?

Example:

```text
Thread:
Should I buy a new laptop?

Thinking:
...

Decision:
I'll keep the current laptop.

Status:
resolved
```

It should remain searchable in history.

Resolution does NOT mean deletion.

---

# 19. ARCHIVING

Do not make Archive a major V1 concept.

Resolved and Dropped Threads can simply become historical.

If the application later becomes large, V2/V3 can introduce archive behavior.

# 20. DATA MODEL

Use PostgreSQL through Supabase.

Prefer normalized tables over giant JSON objects.

Suggested core schema:

## profiles

```sql
profiles
---------
id uuid primary key references auth.users(id)
username text unique not null
created_at timestamptz
updated_at timestamptz
```

Do not store sensitive information unnecessarily.

---

## journals

```sql
journals
---------
id uuid primary key
user_id uuid not null references auth.users(id)
journal_date date not null
created_at timestamptz
updated_at timestamptz
```

Constraint:

```text
one journal per user per date
```

Use a unique constraint on:

```text
(user_id, journal_date)
```

---

## thoughts

```sql
thoughts
---------
id uuid primary key
user_id uuid not null references auth.users(id)
journal_id uuid not null references journals(id)
thread_id uuid nullable
position integer not null
title text not null
created_at timestamptz
updated_at timestamptz
```

A Thought may optionally connect to a Thread.

---

## threads

```sql
threads
-------
id uuid primary key
user_id uuid not null references auth.users(id)

title text not null

status text not null

created_at timestamptz
updated_at timestamptz
resolved_at timestamptz nullable
dropped_at timestamptz nullable
```

---

## thread_notes

Use this table for the actual thinking/history.

```sql
thread_notes
------------
id uuid primary key
user_id uuid not null references auth.users(id)
thread_id uuid not null references threads(id)

content text not null

created_at timestamptz
updated_at timestamptz
```

The user-facing UI should NOT call these "Thread Entries."

Call them:

- notes
- thinking
- updates
- history

depending on context.

---

## decisions

Decisions can be stored separately because they have semantic value.

```sql
decisions
---------
id uuid primary key
user_id uuid not null references auth.users(id)
thread_id uuid not null references threads(id)

content text not null

created_at timestamptz
```

However, if implementation simplicity is better, decisions may initially be represented as a special note type.

Choose the simplest architecture that preserves the information.

Do not create unnecessary abstraction.

---

## tasks

```sql
tasks
-----
id uuid primary key
user_id uuid not null references auth.users(id)

thread_id uuid nullable

title text not null

status text not null

created_at timestamptz
updated_at timestamptz
completed_at timestamptz nullable
dropped_at timestamptz nullable
```

A Task may exist without a Thread.

---

## journal_thread_revisits

Consider a join table if the same Thread can be revisited multiple times in journals.

```sql
journal_thread_revisits
-----------------------
id uuid primary key
user_id uuid not null references auth.users(id)
journal_id uuid not null references journals(id)
thread_id uuid not null references threads(id)

created_at timestamptz
```

This allows:

```text
Oct 1 → Thread A
Oct 4 → Thread A
Oct 9 → Thread A
```

without duplication.

# 21. DO NOT OVER-NORMALIZE

The above is a conceptual model.

Before implementation, inspect whether every table is truly necessary.

The coding agent should prefer:

- understandable schema
- easy queries
- strong RLS
- maintainability

over theoretical purity.

# 22. SECURITY

This application contains private personal thoughts.

Security is a first-class requirement.

Every user-owned table MUST have Row Level Security enabled.

Every query must enforce ownership through `user_id`.

A user must never be able to:

- read another user's journal
- read another user's thoughts
- read another user's Threads
- read another user's tasks
- modify another user's data
- delete another user's data

Do not rely only on frontend filtering.

Security must be enforced at the database level.

---

# 23. SUPABASE AUTHENTICATION

The user explicitly wants:

**username + password only**

No:

- Google
- GitHub
- OAuth
- phone
- social login
- unnecessary authentication methods

Important technical constraint:

Supabase Auth natively works primarily with identities such as email/password and does not provide a simple first-class arbitrary-username/password login flow.

DO NOT solve this by:

- storing plaintext passwords in PostgreSQL
- hashing passwords manually in the frontend
- implementing insecure custom authentication
- exposing the Supabase service-role key to the browser
- creating fake authentication logic entirely client-side

Instead, choose a secure Supabase-compatible architecture.

Preferred approach:

Use Supabase Auth as the actual authentication system while providing a username-only UI.

If username-only login requires a secure server-side mapping between username and the underlying Supabase Auth identity, implement that mapping through a Supabase Edge Function or another secure server-side mechanism.

The service-role key must NEVER be exposed to the frontend.

The user should see only:

```text
Username
[________________]

Password
[________________]

[ Log in ]
```

and:

```text
Create account

Username
[________________]

Password
[________________]

Confirm password
[________________]

[ Create account ]
```

No email field should be exposed if the chosen architecture can securely support the requested username-only experience.

If Supabase requires a configuration step, Edge Function, database function, or dashboard setting, STOP and clearly instruct the user exactly what to do in the Supabase dashboard.

Do not silently invent credentials or configuration.

# 24. SUPABASE DASHBOARD INSTRUCTIONS

Whenever a Supabase dashboard action is required, tell the user:

1. Where to click.
2. What to create.
3. The exact value/configuration.
4. Why it is needed.
5. What result they should see.

Example:

```text
SUPABASE STEP REQUIRED

Open:
Supabase Dashboard → Your Project → Authentication → ...

Create/configure:

...

When finished, tell me "done" and I will continue.
```

Do not assume the user knows Supabase.

Do not ask the user to paste secrets into the chat unless absolutely necessary.

Never ask for:

- service role key
- database password
- JWT secret
- other sensitive credentials

If a secret is required, explain where it belongs and how to configure it safely.

# 49. DATA OWNERSHIP

The user owns their data.

The architecture should make it possible to export their data later.

V2 could support:

```text
Export my data
```

Possible formats:

- JSON
- Markdown
- CSV

Do not implement this unless V1 architecture makes it easy.

But avoid a design that makes export impossible.

# 50. DELETE BEHAVIOR

Be careful with destructive actions.

For important Thread deletion:

Use confirmation.

Example:

```text
Delete this Thread?

This will remove its thinking history and associated data.

[Cancel]
[Delete]
```

However, "Drop" should NOT require deletion.

Dropping means:

> Stop carrying this forward.

The historical record should remain unless the user explicitly deletes it.

---

# 51. ERROR HANDLING

Errors should be human.

Bad:

> PostgreSQL error 23503

Good:

> We couldn't save this right now. Your writing is still here. We'll try again.

Do not expose raw database errors to the user.

Log technical details for development.

---

# 52. LOADING STATES

Use skeletons or subtle loading states.

Avoid spinners everywhere.

For writing areas, avoid disruptive loading states.

The user should be able to start typing immediately when possible.

---

# 53. ACCESSIBILITY

Implement:

- keyboard navigation
- visible focus states
- semantic HTML
- proper labels
- sufficient contrast
- accessible buttons
- screen-reader-friendly icon buttons
- reduced-motion support where appropriate

Do not sacrifice accessibility for aesthetics.

---

# 54. ANIMATIONS

Use subtle motion only.

Examples:

- modal opening
- task completion
- navigation
- expanding Thread sections

Avoid:

- bouncing elements
- excessive transitions
- distracting animations

The app is supposed to calm the user, not stimulate them.

# 70. RLS

Create RLS policies for every user-owned table.

Typical rule:

```text
auth.uid() = user_id
```

For child tables where ownership is indirect, carefully enforce ownership.

For example, if a Task belongs to a Thread, do not assume the client is trustworthy.

Ensure the authenticated user owns the Thread before allowing access.

Test RLS.

# 71. RLS TESTING

- create own journal
- read own journal
- update own journal
- create own task
- read own Thread

Cannot:

- read User B's journal
- read User B's Thread
- update User B's task
- delete User B's data

This is mandatory.

# 73. PERFORMANCE

Priorities:

# 74. LOCAL DRAFT PROTECTION

1. Preserve the local draft.
2. Do not erase it.
3. Retry save.
4. Clearly communicate if it is not yet synced.

This is especially important because the app contains personal writing.

# 87. IMPORTANT PRODUCT RULE

The app should never imply that every thought must become an action.

Valid outcomes include:

```text
Thought → Action
Thought → Decision
Thought → Continue later
Thought → Resolved
Thought → Dropped
Thought → Nothing
```

All of these are successful outcomes.

# 88. IMPORTANT PRODUCT RULE

Do not automatically convert thoughts into tasks.

If AI or automation is added later, suggestions must always be optional.

---

# 89. IMPORTANT PRODUCT RULE

Do not delete history just because something is completed.

The user's history is valuable.

The user should be able to look back and see:

> "I thought about this, I made a decision, and then I actually did these things."

---

# 90. IMPORTANT PRODUCT RULE

A Thread may return to the user's mind repeatedly.

That is normal.

The app should make returning to an existing Thread easier than creating a duplicate.

---

# 91. IMPORTANT PRODUCT RULE

A Task can exist without a Thread.

Do not force everything into the journal.

---

# 92. IMPORTANT PRODUCT RULE

- new Thoughts
- revisited Threads
- direct observations
- decisions
- actions
